## 2. Назначение программы и рабочий процесс

Auto Editor — локальное Windows-приложение для автоматизации монтажа спортивных прогнозов. Историческое имя пакета hockey_editor сохранилось, хотя есть два профиля: ru_hockey (русский хоккейный ведущий) и uz_football (узбекский футбольный ведущий).

Вход: одна/несколько записей ведущего, полный TXT-сценарий либо сценарии отдельных разборов, записи матчей/готовые вставки, логотипы, музыка, материалы дисклеймера, Telegram и подписки. Проект хранит ссылки на исходные файлы, настройки и монтажные планы, а не сами медиа.

Обычный путь пользователя: открыть проект → «Настроить полный выпуск…» → импорт сценария и назначение материалов → выбор отдельного разбора или «Все разборы» → поиск игровых эпизодов/«Определить тайминги» → редактируемая монтажная дорожка → предпросмотр → экспорт MP4.

Полный выпуск: дисклеймер целиком → вступление → последовательность разборов → переход к итогам → повторы прогнозов и прощание. На видео накладываются карточки команд, ставки, статистика, Telegram и подписка. Есть наезды 100–120%, переходы, очистка голоса, музыка, цветокоррекция и автоповорот. Предпросмотр собирается в 640×360; экспорт поддерживает 720p/1080p, 30 fps, сопровождается разметкой JSON/SRT.

У русского профиля исходно акустическое сопоставление со сценарием; при неустойчивом полном выпуске применяется локальный ASR по словам. У узбекского профиля фактическая речь распознаётся и сопоставляется с разделами и прогнозами сценария. Правильный текст прогноза берётся из сценария, время — из речи.

## 4. Модель данных и технические инварианты

- Project.version = 7; загрузчик принимает форматы 1–7. Профили ru_hockey/uz_football.
- Блок имеет стабильный uid, kind (intro/analysis/outro), language, script, source_hint, asr_lines, speech_key, speech_cards, events, edit_plan/edit_key.
- У проекта есть host/hosts, blocks, intro/outro, assets, recording_times, full_video, whole_episode, episode_plan/episode_key.
- Пути при сохранении делаются относительными, при открытии разрешаются относительно файла проекта; учитываются Windows-разделители. Запись через временный файл и replace.
- Plan хранит source_start/source_end, keep, lines, inserts, cards, warnings, duration, sections, media. Не смешивать время исходника и время результата после удаления пауз/добавления дисклеймера.
- forecast_id связывает основную ставку с её повтором. Перестановка повторов не должна менять их владельца. episode.store_episode синхронизирует текст с основным прогнозом.
- validate_plan проверяет границы, минимальную длину, пересечения игровых вставок, доступность файлов, целостность речи/media/sections. Не убирать эти проверки массово ради обхода одного сбоя.
- Межблочные промежутки и сокращение пауз внутри речи — разные механизмы. Разрывы между явно заданными блоками должны вырезаться даже при выключенном сокращении пауз.
- Длинная тишина сама по себе не доказывает неудачный дубль. Произнесённую речь нельзя автоматически удалять только по этому признаку.
- Игровые записи используются как картинка: их звук не должен попадать в выпуск. Голос ведущего и добавленная музыка продолжаются. Дисклеймер сохраняет собственный звук; подписка используется без своего звука.
- Рендер защищает исходники и не перезаписывает существующий целевой MP4.
- Лимит исходника ведущего: 1800 секунд. RU — без фиксированного лимита числа разборов; UZ — по-прежнему 1–4, включая ограничения импортера и EpisodeEngine.
- УЗ-профиль допускает одну очную встречу на разбор; отсутствие игровой записи может оставить ведущего.
- Telegram привязан к произнесённой фразе о канале/ссылке. Нельзя произвольно растягивать его на соседнюю подписку/прощание.
- optional_subscription пропускает анимацию целиком с предупреждением, если она не помещается. Не удлинять прощание и не обрезать анимацию вместо этого правила.

- uz_speech.prepare перестраивает asr_lines/speech_cards, очищает events/edit_plan/edit_key и общий episode_plan/key; учитывать риск потери ручных монтажных правок при новой разметке.
- uz_forecasts работает по словам, а не только по исходным ASR-сегментам. Делит на clauses и собирает окна; учитывает команды, порядковые указания, рынок, числовой тотал и направление.
- match_forecasts выбирает по одному непересекающемуся интервалу для каждого владельца, допускает любой порядок повторов (поиск по маскам подмножеств).
- Названия, отвергнутые рядом с emas, игнорируются. Слабое фонетическое сходство с чужим клубом не должно побеждать явный номер разбора.
- Явные противоречия 1X/X2, победа/двойной шанс, over/under, 1,5/2,5 не должны молча заменяться сценарием.
- needs_review — диагностический флаг и сообщения с временем, а не полноценный пользовательский механизм подтверждения.

## 8. Открытые проблемы, ограничения и пожелания

1. **Гибкая проверка спорной речи пользователем.** В контексте проекта пользователь просил возможность подтвердить/исправить/пропустить сомнительные фразы, чтобы не ждать очередного программного исправления. В текущем коде есть warnings/needs_review и монтажная дорожка после анализа, но некоторые ошибки привязки всё ещё прерывают анализ до неё. Полноценный возобновляемый этап ручного разрешения не подтверждён как реализованный. Это кандидат на следующую большую задачу, не готовая функция.
2. **Мало текстовых плашек в UZ.** Режим «Чаще» регулирует игровые вставки, а не количество текстовых карточек. Нельзя обещать обратное. Извлечение фактов/статистики зависит от ограниченного набора правил и ошибок ASR, в том числе чисел словами. Пользователь просил учесть это в будущем, без отдельной сборки только ради замечания.
3. **Сопоставление фактов со сценарием.** Для ставок это уже используется. Более полное извлечение корректной статистики/фактов из сценария с таймингом фактической речи остаётся направлением улучшения; не заявлять, что все такие карточки уже реализованы.
4. **Telegram.** Ранее на участке около 06:39–06:44 искажённое название канала приводило к пропуску, несмотря на наличие времени. В 0.7.10 добавлен контекстный поиск и ранее проверен пример, но универсальной гарантии нет. Контекстный кандидат помечается needs_review, проверяется связь со сценарием, не должен захватывать соседний CTA.
5. **Блокирующие ошибки остаются.** Не найдено начало, переход к итогам, прогноз/повтор; явное противоречие ставки; невозможно выбрать непересекающиеся интервалы; нет обязательного материала или повреждён план. Решать адресно, не выключать все проверки.
6. **UZ максимум четыре разбора**, RU без фиксированного предела. Это текущая функциональная граница, не случайно пропущенное исправление 0.7.7.
7. **Непроверенные реальные выпуски.** Успех набора тестов не гарантирует любую дикцию, самоисправления и пересказ. Не обвинять ведущего или язык без анализа конкретной записи.
8. **Отсутствуют пользовательские архивы в текущем окружении.** Упоминание имени архива в переписке не означает, что он доступен для чтения. Для повторного реального рендера могут понадобиться файлы заново.
9. **main устарела относительно рабочей ветки.** Это риск организации репозитория. Не выполнять merge, смену default branch или перенос кода автоматически в задаче передачи.

## 9. Что проверяли и что не работало

Неудачные прежние подходы: запрет пауз >3 секунд; ожидание порядка повторов как в сценарии; только буквальное X2; обработка целиком по ASR-сегментам; трактовка отвергнутого названия как действительного; чрезмерное доверие похожему слову; остановка выпуска из-за необязательной подписки; буквальное распознавание названия Telegram. 1. Прочитать этот файл и проверить remote HEAD именно version-0.7. Документационный коммит окажется поверх 37861b2; не перепутать его с новой версией приложения.

3. Сначала воспроизвести сбой на имеющихся данных, не начинать с замены модели или удаления кеша.
4. Если запрошена система подтверждений — спроектировать сохранение ручных решений, точные интервалы/прослушивание, исправление текста/владельца и возобновление анализа. 6. После разрешённой разработки проверить затронутые регрессии и конкретный выпуск с таймкодами/без них, включая прощание, подписку, Telegram, принадлежность и непересечение повторов. Windows CI необходим для проверки готового EXE.
7. Не запускать эти шаги разработки автоматически только потому, что они перечислены в передаче.

Команды разработки из корня актуальной ветки:
```sh
python -m pip install -r requirements.txt

python main.py --self-test source-check.json
```
